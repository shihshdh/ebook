# 交接：手机端流畅度（分支 `perf/mobile-smoothness`）

接手的人先读完这页。用户要求：**极致丝滑、不偷工减料、不许把动画调快**（「我要的是丝滑，不是动效加快」）；视觉不能变。
用户笔记本容易过热：测完关掉 vite preview、浏览器、Gradle。

### 第二轮（云端做的，提交 `6884244`、之后那个）

探索页滚动的真凶是**衬线字体分片**，不是排版本身。`tokens.css` 引的 Noto Serif SC（fonts.loli.net）每个字重切成 101 片、一片中位 64KB，
哪片里的字第一次上屏才下哪片。实测（4 倍降速）：
- 分片没到时排字要逐字走系统后备字体：12 个生僻字 16–44ms；分片到了同样的字 0.3–1ms。
- 每个分片下到时，浏览器把屏幕附近**所有**用这套字的文字重排一遍（170 个对象，17–28ms），不管下到的字有没有用上。
- 书目 4357 本、书名 2551 个字：前 18 本书名就要 19 片，前 90 本也只要 24 片——往后每页只多 0–5 片，多预取几页几乎不多下流量。
- Chrome 的 content-visibility: auto「附近」是视口上下各 **1.5 屏**（实测约 1266px）。原来哨兵提前 900px，新挂的卡片一挂上就在附近，当帧全排。

改了什么：
11. `src/lib/fonts.js`（新）：`loadSerif(text, weight)` 用 `document.fonts.load` 只下这段字要的分片；`atMost(promise, ms)`。
12. `src/effects/MasonryWall.jsx`：书名 + 摘句的分片一次预取 4 页（`FONT_PAGES`），快用完时再下一批（到达挤在一起，同一帧到的只重排一次）；
    哨兵到了等分片下好再挂（最多 `FONT_WAIT` 500ms，离线 / 字体被拦照样挂，测过）；哨兵提前量 900px → `200%`（比 1.5 屏远，新卡片先占位不排）；
    追加一页放进 `startTransition`；换书单直接从第一页算起（以前先按旧张数渲染一遍再砍）。
    文字卡也 content-visibility: auto，占位高度用 `estimate()` 内联（估差主要来自长书名的出处行折行，只影响屏幕外占位；**列分配没动**，瀑布流排列和原来一样）。
    `warm.js` 的 LAZY 也包含文字卡。
13. `src/App.jsx`：每页外面套一层固定的路由地址上下文（`UNSAFE_LocationContext`）。`<Routes location>` 自己订着当前地址，
    地址一变（切页、搜索框同步到地址栏）就给整页换新上下文，后台页里用 useNavigate / Link 的组件全部重渲染——`Pages` 的 memo 挡不住。
14. `src/pages/Search.jsx`：结果列表抽成 memo 的 `ResultList`（以前每敲一个字，结果还没变也把 30 行重新生成比对）；`open` 用 useCallback + ref；
    `pooled` 只依赖 `by` 参数而不是整个 params。`src/lib/library.js` 的 `prepareSearch`：空闲时先把每本书的折叠写法算好（第一次搜索要现算四千多本）。
    `src/lib/pool.js`：书名归一化结果缓存（上限两万条）。

### 第三轮（本机）：打开书详情

**先查清原因**（`TRACE=sheet-open` + `fontev.mjs`、页面里看 `document.fonts`）——和上面猜的不一样，**不是分片没下**：
- fonts.loli.net 的 CSS 里 400 / 600 / 900 三个字重指向**同一批文件**（可变字体，按字切 101 片）：下一片三个字重一起就绪。
  瀑布流预取 600 字重的书名、摘句，书详情 700 的书名、400 的简介用到的分片也就下好了。sheet-open 整个场景里一个字体请求都没有。
- 点开那一帧的两块：① 脚本 19–30ms：后台页（插件页一长串书源 Link、首页、书架……）跟着重渲染；② 样式布局 ~44ms，其中排字 ~30ms。
- 排字慢的原因：**字形第一次以某个「字重 × 字号」出现时要现算字形数据**，和分片下没下无关。实测（4 倍降速，分片都已下好，60 个字）：
  第一次 14–39ms，同样的字打乱顺序再排 0.6–1.6ms；换个字号（15px → 15.5px）又是 36ms。约每个新字形 0.5–1ms。
  书详情的书名（700、24px）、简介（400、15px）是别处没用过的组合，所以每本书的字都是冷的。同一本书关了再开（字形全热），最长帧 37–53 → 13–20ms。

### 手感（2026-10-10，提交 `ebdc807`）

起因：朋友反馈「翻页要用点力，按番茄的力度不够」。用户选了：**翻页完全跟手**、**触屏按下反馈**、**关键时刻轻震**（下拉书签到位、光盘换片停稳；翻页不震）。
`scripts/perf/touchtest.mjs`（手机模拟 + 真触摸事件）新旧对照：

| 项目 | 旧版 | 现在 |
|---|---|---|
| 阅读器 轻拨 20px（~80ms）/ 24px（~40ms） | 不翻 / 不翻 | 翻 / 翻 |
| 斜着轻拨（横 24 竖 18）、往右轻拨 | 不翻 | 翻 |
| 慢拖 30px 停住再松 / 慢拖 60px / 拖过去又往回甩 | 不翻 / 翻 / 不翻 | 同左（不变） |
| 拖到一半被打断（touchcancel） | 书页停在 -27px | 回原位 |
| 连拨三下（间隔 60ms） | — | 翻三页 |
| 拖动时书页 | 整页只挪 35%、变淡 | 1:1 跟手，露出真实的下一页（章节交界照旧） |
| 书详情 往下拖 200px / 往下甩 60px | 关不上 / 关不上 | 关上 / 关上（往上推照常滚动） |
| 首页光盘 快甩 60px | 弹回原来那张 | 换一张 |
| 书卡按住 240ms | 没反应 | 缩到 0.97，抬手回弹；按着就划走不缩 |

几处要知道的：
- **iframe 里的触摸坐标会被书页平移抵消**：书页（连同 iframe）跟着手指走，iframe 里的 clientX 就少算了平移量。阅读器里一律换算成外层坐标（加 iframe 的 rect），
  而且要在「收尾动画走完」**之前**换算（连拨时第二下按下，iframe 还在动画中途）。
- **书详情下拉以前根本拖不下来**：面板 `touch-action: pan-y`，指针事件一往下动浏览器就接管滚动、发 pointercancel。改用触摸事件 + 非 passive 的 touchmove（只在内容到顶、往下拉时 preventDefault）。
- Chrome 会把点按容差里的移动合并掉，轻拨往往只来一两个 touchmove：速度门槛不能高（翻页 200px/s，书详情关闭 400px/s）。
- 按下反馈用 WAAPI 动 `scale` 属性（`lib/press.js`），不改各元素原有的 transition；所有 `:hover` 规则收进 `@media (hover: hover)`，触屏不再卡悬停样式。
- 跟手翻页的收尾时长沿用原来的（翻过去 300ms、弹回 .35s），没有加快。

### 第四轮（本机）：搜索打字（提交 `e908fc2`）

**原因**（`TRACE=search-type`）：打出第一个字那帧任务 121ms，其中排版 95ms，几乎全是排字（ShapeText），没有字体下载——
字形第一次以某个「字重 × 字号」出现要现算（和第三轮同一回事）。一次挂 30 行，行是 content-visibility: auto，但离屏幕 1.5 屏以内的
10 行当帧全排，近两百个冷字形；手机上（390×844）结果从 523px 才开始，看得见的只有 3 行（78 个字形）。往下滚时还有两次「排字时才发现分片没下」。

改了什么（`src/pages/Search.jsx`、`src/lib/glyph-warm.js`）：
17. **分帧挂**：新词第一帧只挂看得见的几行（按结果列表起始位置 min(46vh, 420px)+100 估、多一行余量）；打字停下 250ms 后每帧加一行，挂满「附近」（2.5 屏）后剩下的一次挂上。
    换词时上个词已经挂着的行原地留着（和原来一样不重挂、不重新淡入）。
18. **入场动画逐毫秒不变**：晚挂的行把 reveal 动画的 `startTime` 对齐到这个词第一批行的开始时刻（CSS 的 i×30ms 延迟照旧）。
    `revealcheck`（临时脚本）实测各行开始淡入 0/30/60…420ms，和原版一样。**坑**：先试过按渲染时刻扣延迟，第一批行真正开始动画还要晚一个渲染加排版，晚挂的行早了 60ms；
    `getAnimations()` 会强制样式 + 排版（Chrome 有滚动驱动动画以后），不能在提交里调——书源结果每回来一次就多排一遍，攒到 rAF 里一起做。
19. **行级 memo**：搜索池每次生成新的书对象，按 id + 下载入口个数比（书源合并一定会加下载入口）。以前每挂一行、每来一个书源结果，30 行全部重来（4 倍降速十几毫秒）。
20. **书名分片预取**：换词、加载下一批时成批 `loadSerif`（只在这两种时候，书源结果一变就重下一遍会白白多一截），屏幕外的行等它（最多 500ms）再挂。
21. **结果行共用字空闲预热**：`glyph-warm.js` 加 `warmIdle`（requestIdleCallback 里一小段一小段排），把标签、出版社和状态、来源那一行的字按结果行样式先排一遍——
    第一屏约四成的字是它们。打第一个字那帧排版 46 → 28ms。
22. 「继续往下翻」哨兵等这一批挂完才放（列表还短时它就在附近，会提前多拉 30 行）。

### 第七轮（云端）：底栏滑块

用户：「底部栏的滑块感觉不够圆润，你看看 iOS 是咋做的」。本地那一轮查清了原因、定了方案（用户选的：**动画真正播出来 + 两头正圆的胶囊 + 外框也变全胶囊**），
但那一版每帧改宽度，切页变慢（插件 → 首页那两帧绘制各多 20–25ms），没提交。云端按同一方案重做：

原因（本地查到的）：
- 手机底栏是 `position: fixed`，`offsetParent` 永远是 null，旧代码以为底栏没显示，滑块每次直接**瞬移**，液态动画在手机上从没播过。
- 旧的拉伸是整块 `scaleX`，圆角跟着拉扁；而且滑块是圆角矩形（半径 20），不是胶囊。

改了什么（`src/components/NavBar.jsx` 顶上的注释有全部细节；`app.css` / `light.css` 的 `.liquid-thumb`、`.lt-clip`、`.lt-cap`）：
30. **形状**：左右两半各是一个整条导航那么长的胶囊，套在 overflow: hidden 的框里只露出一截，在胶囊中段平直处拼起来。拉长 = 两半各自位移，
    移动中变细 = 等比缩放，两头始终是正圆。底栏外框半径 = 高度一半，滑块上下各让 6px（加 1px 边框），两条圆弧同心。电脑顶栏用同一套
    （本来就是胶囊，静止时新旧逐像素最大差 9 个色阶，看不出来）。
31. **动画**：弹簧轨迹一次算好（每 1/120 秒一个点，弹簧本身仍按 1/240 秒积分），WAAPI 交给合成线程播，只动 `translate` / `scale`——
    切页时主线程再忙，滑块也不停；全程不重绘、不重排。中途改点从当前位置和速度接着弹（实测连续）。
    不支持 `linear()` 的旧 WebView（Chrome 113 以前）直接落位。各格位置在 ResizeObserver 里量好缓存，点击时不逼浏览器当场排版。

几处坑（都实测过）：
- **拼接点必须是整 CSS 像素**（框自己的坐标里）：合成器把两个裁剪框往外扩成整数，不是整数时中间那列被半透明的滑块画两遍，是一条亮线——
  3 倍屏上 70.333px（正好是整设备像素）也会；容器本身在屏幕上偏半个像素反而没关系。所以两个框跳格取整，胶囊的曲线里同一时刻把框的跳动扣回来。
- **关键帧要少**：第一版每个动画 130 多个关键帧，切页那次强制样式计算多 10–27ms（浏览器逐对建插值），切页卡顿均值 15 → 111。
  改成每个动画只有起止两帧、曲线写在 `linear()` 缓动里；位移按「整数 ÷ 1024」编码（浮点精确，合成器算回来还是整数）。
- **曲线的点也要少**：拼字符串、浏览器解析都花时间（240 点/秒时一次切页 4–5ms，4 倍降速）。改成 120 点/秒，拼接点能不动就不动
  （离线模拟全部标签组合：平均只跳 4–11 次，没有一段落到平直段外面）。
- **平时不占合成层**（不写 will-change）：常驻 6 个合成层时，首页滚动每帧的分层、提交多一截（主线程多 7%）；现在动画时浏览器自己建层，播完撤掉。
- 「暂停动画再截图」测不到合成线程上的接缝（暂停的动画可能退回主线程画）。用 `scripts/perf/thumbcheck.mjs`：调试协议把动画放慢 20 倍，真实播放中连拍。

云端 A/B（每次新开浏览器，交替；对照是 `76f9d0e`，手机上滑块瞬移、什么都不做）：

| 场景 | 对照 | 现在 |
|---|---|---|
| 切页 卡顿 | 75 / 26 / 67 / 55 / 55（均 56） | 86 / 44 / 67 / 32 / 81（均 62） |
| 切页 最长帧 | 83 / 83 / 100 / 67 / 83 | 117 / 83 / 100 / 67 / 100 |
| 切页 >33ms 帧 | 6 / 6 / 6 / 5 / 5 | 7 / 7 / 8 / 5 / 5 |
| 首页滚动 >33ms 帧（去掉常驻层那版测的，之后只少了曲线的点） | 20 / 14 / 34 / 12 | 15 / 12 / 18 / 19 |

云端噪声大（同一版本切页卡顿 26–75），本机请再复测一次切页（`ab.mjs`，4 轮以上）。滑块从「不动」变成「真的在动」，主线程多的只有建动画那一下。

### 第八轮（云端）：首页的唱片架、预排版流水线

32. `src/effects/DiscShelf.jsx`：停稳以后每张盘挂一个**无限循环的 transform 动画**——起止两帧是完整的 transform，只差最后的 `rotateZ` 多转 360°，
    浏览器逐项插值，就是匀速自转，合成线程播，rAF 停下。一有拖动、换盘（`wake()`），撤下动画、按同一个「转了多久」的钟接着用 rAF 写，停稳再挂回去；
    钟只在看得见时走（和以前 rAF 停转一样），撤动画时按动画实际转到的时间拨钟，接得上。新挂上的盘（`visible` 变了）重摆一遍再挂。
    - 静置 4 秒（4 倍降速、唱片架在屏幕中间）：主线程 **1668ms → 164ms**（样式、rAF、提交都是 0）。
    - **坑**：第一版另包一层 `.disc-spin` 只转那一层——每张盘多两个渲染面（投影滤镜一个、外层 3D 变换压平一个），
      唱片翻页时合成线程忙到主线程每次提交干等 29–70ms，卡顿合计 0 → 4000。动画必须挂在盘本身上，渲染结构和原来一样。
    - 「减少动态效果」下新旧逐像素一致；方向键、甩动换盘、停稳后 1 秒内盘上 0 次样式写入，都测过。
    - A/B（3 轮，对照 `cfddc7e`）：唱片翻页卡顿 0/0/0 对 0/0/17、慢帧相当；首页滚动 >33ms 帧 5/14/14 对 12/12/10；切页卡顿 52/76/367 对 50/35/41。
33. `src/App.jsx` 预排版流水线：操作事件里只记时间、停掉正在排的，计时器到点自己看停手够不够 1.2 秒。
    以前每个滚动 / 指针事件都清计时器、重设、再把下一步找一遍（`querySelectorAll` 之类）——首页一次滚动里 426 次、共 339ms（调试构建、4 倍降速）。
    开 App 静置 15 秒，两版都挂好 4 个后台页、预排 314 块。

### 第九轮（云端）：切页的样式重算、订阅页预渲染、开屏排序

34. `src/styles/app.css` + `src/App.jsx`（`9ed7000`）：后台页动画暂停规则 `.route.is-kept * { animation-play-state: paused }` 换成 `.route[data-unseen] *`。
    - 原来那条：切页时 `is-kept` 一摘一挂，类在祖先上、后代是通配符，浏览器只能把进来那页**每个元素**重算样式（第一次进探索 305 个、4 倍降速三四十毫秒）。
    - 查下来它对**去过的页本来就不起作用**：`content-visibility: hidden` 的页里不算样式，规则落不到元素上——入场动画没播完就切走的、
      探索页的慢漂移在后台照样按时间走完（逐步记了 `document.getAnimations()` 的状态，原版就是这样）；后台的循环动画浏览器也不跑
      （停在书架 5 秒，样式重算次数和全停时一样）。
    - 它真正管用的只有空闲预渲染挂上、**还没去过**的页：预排版时样式算过，入场动画已经建好，要停在开头等第一次点进去。
      所以只给没去过的页挂 `data-unseen`（App.jsx 记 `seen`），第一次进去时摘一次，之后切页只动 route 自己。

### 首页滚动（没解决，查到的）

首页滚动是唯一没比原版好的场景（最长帧 63–80，常有一帧 50ms 以上）。慢帧里大头是 **PrePaint 的 CompositingInputs**（24 / 39 / 54ms），
发生在首页 `.home-lazy` 区块（第一轮加的 content-visibility: auto）滑进视野、解锁的那一帧。试过的（都是 4 次交替 A/B 或单测）：
- 去掉 `.home-lazy` 的 content-visibility：首页滚动卡顿 16 → 0、最长帧 77 → 25；但切页卡顿 8 → 39、最长帧 85 → 270，唱片翻页最长帧 60 → 160（退回原版）。没合。
- 只去掉 overflow-clip-margin：没变化。
- 把后台页逐个 display:none：没变化（不是后台页的分层拖的）。
- 不预排首页区块（静置 3 秒就测）：合成输入只有 4ms，但解锁那帧排版 180ms。
- 首页区块预排少拆几层（warm.js DEPTH 2）：没变化。
结论：区块预排过（排版有了）以后，解锁时合成输入要现算 25–55ms，预排版做不到这一步。没想到不牺牲切页 / 唱片翻页的办法，留给下一步。

## 发版

`发版.bat`（项目根）：`node release.mjs --check`（在 main、工作区干净、和 GitHub 上的 main 一致、四处版本号一致、有正式签名、有更新说明）
→ `打包桌面版.bat` → 安装包复制到 `release/` → `打包安卓版.bat` → `gradlew --stop` → `node release.mjs`。
`release.mjs`：算 SHA-256；**先**建 Release `v<版本>`、传两个文件（`gh release create`），核对附件都在，**再**改 `latest.json` 和 README 的下载链接、推 main。
顺序反过来的话，客户端读到新清单、附件还没传完，点更新会 404。没装 gh：正文写在 `release/RELEASE_BODY.md`，网页上手动建好后跑 `node release.mjs --manifest`。
包比当前代码旧（之前打的）、没有 `android/keystore.properties`（APK 不是正式签名、装不上去覆盖旧版）都会停下。
